Contexto · 1 de 2

La regla que debemos proteger

Una historia clínica solo puede guardarse si el médico existe. Médicos vive en PostgreSQL; Historias vive en MongoDB.

01

Antes

Historias llamaba directamente a la API HTTP de Médicos mediante OpenFeign.

02

Problema

La integración conocía el verbo, la ruta HTTP y la disponibilidad inmediata de otra instancia.

03

Ahora

Historias publica un mensaje; RabbitMQ encuentra un consumidor y correlaciona la respuesta.

La API pública sigue siendo REST. Solo cambia el transporte interno entre los dos dominios.

Contexto · 2 de 2

¿Por qué introducir un broker?

Desacoplamiento espacial

El productor no conoce la IP, el puerto ni la cantidad de instancias de doctor-service.

Amortiguación

La cola retiene solicitudes brevemente cuando el consumidor está ocupado.

Distribución de carga

Con varias instancias consumidoras, RabbitMQ entrega cada mensaje a una sola de ellas.

Observabilidad

Conexiones, canales, colas y tasas de mensajes pueden verse en el panel de administración.

RabbitMQ desacopla el destino físico; no elimina el contrato entre servicios ni vuelve asíncrona automáticamente toda la operación.

Comparación · Eventos vs. HTTP

Qué gana un flujo realmente asíncrono

AspectoHTTP síncronoEvento asíncrono
TiempoAmbos servicios deben estar disponibles simultáneamente.La cola conserva el mensaje hasta que el consumidor pueda procesarlo.
AcoplamientoRuta, verbo y formato de respuesta compartidos.Contrato del evento y destino lógico; no conoce al consumidor.
Fan-outEl emisor llama por separado a cada interesado.Un hecho puede alimentar auditoría, alertas y analítica.
PicosAumentan conexiones y timeouts.La cola amortigua la carga y los consumidores avanzan a su ritmo.
Fallo parcialLa caída del receptor afecta inmediatamente al emisor.El emisor puede continuar; el receptor se recupera después.
EscaladoBalanceo de peticiones.Consumidores competidores reparten mensajes.

Importante en este deck: request/reply sobre RabbitMQ sigue esperando una respuesta y no obtiene todo el desacoplamiento temporal de un evento. Para eso, la API debería aceptar el trabajo y completarlo después.

Request/reply · 1 de 3

El flujo completo de una validación

1

Solicitud

Historias envía el ID con convertSendAndReceive.

2

Enrutamiento

El direct exchange hace coincidir la routing key con el binding.

3

Consumo

El listener obtiene el ID y pregunta a DoctorService.

4

Respuesta

El valor retornado viaja a amq.rabbitmq.reply-to.

5

Correlación

El correlation ID entrega el reply a la llamada que lo originó.

6

Decisión

FOUND permite guardar; NOT_FOUND produce 400; timeout produce 503.

El broker transporta mensajes, pero la petición HTTP sigue esperando. Es RPC sobre RabbitMQ.

Request/reply · 2 de 3

Productor: Clinical History Service

Object reply = rabbit.convertSendAndReceive(
    RabbitTopology.EXCHANGE,
    RabbitTopology.VALIDATION_ROUTING_KEY,
    doctorId.toString());

if (reply == null) {
  return DoctorValidationResult.UNAVAILABLE;
}

try {
  return DoctorValidationResult.valueOf(reply.toString());
} catch (IllegalArgumentException unexpectedReply) {
  return DoctorValidationResult.UNAVAILABLE;
}

Contrato pequeño

La solicitud contiene el ID como texto; la respuesta solo puede ser FOUND o NOT_FOUND.

Fallo explícito

Un timeout, error AMQP o reply desconocido se convierte en UNAVAILABLE.

Request/reply · 3 de 3

Consumidor: Doctor Service

@RabbitListener(queues = RabbitTopology.VALIDATION_QUEUE)
public String validate(String rawDoctorId) {
  try {
    Long doctorId = Long.valueOf(rawDoctorId);
    return doctors.exists(doctorId) ? "FOUND" : "NOT_FOUND";
  } catch (NumberFormatException invalidMessage) {
    return "NOT_FOUND";
  }
}

Respuesta automática

Spring publica el valor retornado en el reply-to del mensaje original y conserva su correlation ID.

ACK automático

Con acknowledge-mode: auto, el mensaje se confirma al terminar el listener sin error.

Una carga no numérica se responde como NOT_FOUND para evitar reintentos infinitos de un mensaje inválido.

Timeout de 3 segundos

El cliente deja de esperar, produce UNAVAILABLE y la API responde 503.

TTL de 5 segundos

RabbitMQ descarta una solicitud RPC vieja antes de que un consumidor recuperado procese trabajo inútil.

spring:
  rabbitmq:
    template:
      reply-timeout: 3s

# RabbitTopology.java
QueueBuilder.durable("doctor.validation").ttl(5_000).build();
Confiabilidad · 2 de 2

La API distingue negocio de infraestructura

Resultado
Significado
Decisión HTTP
FOUND
El médico existe en PostgreSQL.
200/201 · guardar en MongoDB.
NOT_FOUND
El consumidor respondió correctamente, pero el médico no existe.
400 · corregir doctorId.
UNAVAILABLE
Broker inaccesible, timeout o respuesta inesperada.
503 · reintentar después; no guardar.

NOT_FOUND no es una caída. Es una respuesta válida del dominio. Mezclarla con UNAVAILABLE ocultaría problemas operativos y confundiría al cliente.

Cierre

Qué logramos y qué sigue

✓

Desacoplamiento

Historias dejó de conocer la API HTTP y las instancias de Médicos.

✓

Fallo seguro

Timeout, TTL y estados distintos impiden guardar sin validación.

→

Evolución

Un flujo realmente asíncrono podría responder 202 y completar después con consistencia eventual.

Idea final: RabbitMQ cambió el transporte y el acoplamiento espacial. La necesidad de una respuesta inmediata mantiene este caso como RPC.
