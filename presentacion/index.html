Propósito del proyecto

Separar los dominios principales del hospital en servicios independientes, con datos aislados, descubrimiento dinámico y un único punto de entrada para los consumidores.

01

Atención clínica

Historias clínicas vinculadas a un paciente y validadas contra un médico existente.

02

Operación desacoplada

Cada dominio evoluciona, se despliega y persiste sus datos sin compartir base de datos.

03

Integración desacoplada

RabbitMQ media la validación: Historias no necesita conocer la URL ni una instancia de Médicos.

Arquitectura · 7 de 7

Comunicación entre servicios

Externa: Gateway → servicios

El gateway delega la solicitud usando el nombre registrado en Eureka. El consumidor no conoce puertos internos ni contenedores.

Interna: Historias → Médicos

clinical-history-service publica el ID en hospital.doctors. RabbitMQ lo enruta a doctor.validation y entrega la respuesta correlacionada.

El transporte ahora es AMQP, no HTTP. El broker desacopla direcciones e instancias; como esta regla exige validar antes de guardar, se usa request/reply con un timeout de 3 segundos.

RabbitMQ · 1 de 5

¿Qué hace un broker de mensajes?

Productor
publica
→
Exchange
decide ruta
→
Cola
espera
→
Consumidor
procesa + ACK

Exchange

No guarda mensajes. Lee la routing key y aplica sus bindings para decidir a qué cola enviarlos.

Queue

Amortigua productor y consumidor. En este proyecto es durable y descarta solicitudes caducadas tras 5 segundos.

Consumer + ACK

@RabbitListener procesa el mensaje. El ACK confirma al broker que puede retirarlo de la cola.

El productor conoce un destino lógico, no la IP, el puerto HTTP ni cuántas instancias consumidoras existen.

  ▼

│ Exchange directo: hospital.doctors                      │
│   binding exacto ───────────────► Queue: doctor.validation│
└──────────────────────────────────────────────────────────┘
                                           │ entrega
                                           ▼
                               doctor-service @RabbitListener
                                           │

Direct exchange

La routing key debe coincidir exactamente con el binding. Es sencillo y apropiado para un comando con un destino claro.

Consumidores competidores

Si hay varias instancias de Médicos, RabbitMQ reparte mensajes; cada solicitud la procesa una sola instancia.

Spring AMQP administra correlationId y amq.rabbitmq.reply-to. Si no llega respuesta en 3 s, el resultado es UNAVAILABLE y la API responde 503.

OpenFeign vs RabbitMQ

AspectoOpenFeign (antes)RabbitMQ (ahora)
TransporteHTTP request/responseAMQP mediante un broker
DestinoNombre en Eureka → instanciaExchange + routing key → cola
AcoplamientoConoce ruta, verbo y DTO HTTPConoce contrato del mensaje y destino lógico
Si el consumidor está ocupadoLa conexión espera o fallaLa cola absorbe picos mientras el mensaje sea vigente
EscaladoLoadBalancer elige instanciaLa cola reparte entre consumidores
Fallo aquíCircuit breaker + fallbackReply timeout + TTL + respuesta 503

Integración · Eventos vs. HTTP

Ventajas de una arquitectura por eventos

CapacidadHTTP síncronoEventos asíncronos
DisponibilidadEmisor y receptor coinciden en el tiempo.El broker conserva el evento mientras el consumidor se recupera.
AcoplamientoServicio, verbo, ruta y respuesta.Tipo y contrato del hecho publicado.
ExtensibilidadAgregar un receptor modifica u obliga a coordinar al emisor.Nuevos consumidores se suscriben sin cambiar al productor.
Picos de tráficoMás conexiones, latencia y timeouts.Cola o log amortigua la carga; cada consumidor avanza a su ritmo.
RecuperaciónLa respuesta es efímera; suele requerir reintentar la petición.Retención, ACK u offsets permiten reanudar procesamiento.
Usos idealesConsultas, validaciones y respuestas inmediatas.Auditoría, notificaciones, integración y procesamiento desacoplado.

No es una sustitución total: HTTP ofrece simplicidad y consistencia inmediata; los eventos ofrecen resiliencia y evolución independiente a cambio de consistencia eventual, idempotencia y mayor operación.

RabbitMQ · 5 de 5

Lo que cambió… y lo que no

Sí cambia

  • Historias ya no conoce la API HTTP de Médicos.
  • El broker enruta, amortigua picos y reparte consumidores.
  • La integración se observa en el panel de RabbitMQ.

No cambia

  • La API pública sigue siendo REST.
  • La historia espera una respuesta antes de guardarse.
  • Si no se puede validar, se rechaza con 503.

Decisión consciente: es RPC sobre mensajes. Un diseño totalmente asíncrono respondería 202 y completaría después, pero cambiaría el contrato y permitiría consistencia eventual.

Flujos · 2 de 3

Resiliencia ante fallos

En el Gateway

Resilience4j vigila cada ruta: ventana de 5 llamadas, umbral de fallo del 50% y 10 s en estado abierto.

Si el destino falla, responde 503 desde /fallback/... en vez de colgar la petición.

Dentro de Historias

RabbitTemplate espera como máximo 3 s. La cola elimina solicitudes vencidas a los 5 s.

Si Médicos o el broker no responden, la creación devuelve 503 y no registra una historia sin validar.

Plataforma · 2 de 3

Dockerfiles multi-etapa

Etapa de compilación

Imagen con Gradle 9.7.1 + JDK 25 (o Go 1.27). Copia primero los scripts de build para que las dependencias queden en una capa reutilizable.

Etapa de ejecución

Solo el JRE 25 (o Alpine para Go) y el app.jar. Se ejecuta con un usuario sin privilegios, no como root.

FROM gradle:9.7.1-jdk25 AS build
COPY settings.gradle build.gradle ./
COPY */build.gradle ./            # capa de dependencias
RUN gradle :doctor-service:dependencies --no-daemon -q
COPY doctor-service/src doctor-service/src
RUN gradle :doctor-service:bootJar --no-daemon

FROM eclipse-temurin:25-jre AS runtime
COPY --from=build .../app.jar app.jar
USER spring
ENTRYPOINT ["java","-XX:MaxRAMPercentage=75.0","-jar","/app/app.jar"]

La imagen final no contiene Gradle, ni el JDK completo, ni el código fuente.

Cierre · 2 de 2

Conclusiones

Arquitectura

Dominios independientes, bases aisladas y APIs enfocadas en una sola responsabilidad.

Conectividad

Eureka sirve al Gateway; RabbitMQ desacopla la validación entre Historias y Médicos.

Operación

Timeout, TTL y ACK hacen explícito qué ocurre con esperas, mensajes vencidos y entregas.

Resultado: Feign salió del enlace interno; la API conserva su comportamiento y la mensajería queda lista para evolucionar hacia eventos realmente asíncronos.
