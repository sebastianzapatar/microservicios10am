Contexto · 1 de 2

Dos formas de comunicarse

HTTP

Necesito una respuesta ahora

El Gateway enruta solicitudes. Historias consulta a Médicos con OpenFeign para validar una regla antes de guardar.

Acoplamiento temporal deliberado.

Kafka

Este cambio ya ocurrió

Cada dominio publica un evento. Auditoría lo procesa después, sin bloquear la respuesta HTTP.

Integración asíncrona y extensible.

Kafka complementa REST: no reemplaza la validación inmediata del médico. Se usa donde la consistencia eventual es apropiada.

Contexto · 2 de 2

¿Qué problema resuelve?

01

Desacoplamiento

El productor no conoce quién consumirá ni cuántos consumidores aparecerán mañana.

02

Reproducción

Los eventos quedan en el log y una vista puede reconstruirse desde sus offsets.

03

Orden por entidad

Una clave estable envía los cambios del mismo agregado a la misma partición.

El resultado es un contrato de eventos común, pero sin compartir bases de datos entre dominios.

Comparación · Eventos vs. HTTP

Ventajas de comunicar mediante eventos

AspectoHTTP síncronoEventos con Kafka
DisponibilidadEmisor y receptor deben responder al mismo tiempo.El productor termina aunque el consumidor esté temporalmente detenido.
AcoplamientoConoce servicio, verbo, ruta y respuesta.Solo conoce el tipo y contrato del evento.
Nuevos consumidoresCada integración exige otra llamada o cambio en el emisor.Auditoría, alertas o analítica se suscriben sin modificar productores.
Picos de cargaSe convierten en conexiones, latencia y posibles timeouts.El log amortigua el pico y cada consumidor avanza a su ritmo.
RecuperaciónLa respuesta desaparece al terminar la petición.Offsets y retención permiten reanudar o reconstruir vistas.
EscaladoSe balancean solicitudes entre instancias.Particiones y grupos distribuyen trabajo en paralelo.

Trade-off: los eventos introducen consistencia eventual, duplicados posibles y más operación. HTTP sigue siendo preferible para consultas y decisiones que necesitan respuesta inmediata.

Go · Pacientes

producer.SendMessage(&sarama.ProducerMessage{
    Topic: "hospital.events",
    Key:   sarama.StringEncoder(key),
    Value: sarama.ByteEncoder(value),
})

Sarama usa WaitForAll, reintentos e idempotencia.

El formato JSON permite interoperar sin compartir código Java con el servicio Go.

Consumidor

Audit Service construye una vista

@KafkaListener(topics = "${hospital.kafka.topic:hospital.events}")
public void receive(DomainEvent event) {
  if (byId.putIfAbsent(event.eventId(), event) != null) {
    return; // reentrega ya procesada
  }
  events.addFirst(event);
  while (events.size() > maxEvents) {
    DomainEvent removed = events.pollLast();
    byId.remove(removed.eventId(), removed);
  }
}

Confiabilidad

Qué garantiza y qué no

MecanismoQué aportaLímite
acks=allEl líder confirma la escritura según el ISR.En local hay un único broker.
Productor idempotenteEvita duplicados producidos por reintentos de red.No deduplica operaciones de negocio distintas.
Clave estableOrden por agregado dentro de su partición.No existe orden global entre las 3 particiones.
Consumidor idempotenteTolera reentrega del mismo eventId.La vista demostrativa vive en memoria.

Siguiente paso de producción: patrón Transactional Outbox para hacer atómica la escritura en la base y el registro pendiente de publicación.

Infraestructura

Kafka en KRaft, sin ZooKeeper

kafka:
  image: apache/kafka:4.1.0
  environment:
    KAFKA_NODE_ID: 1
    KAFKA_PROCESS_ROLES: broker,controller
    KAFKA_LISTENERS: PLAINTEXT://:9092,CONTROLLER://:9093
    KAFKA_ADVERTISED_LISTENERS: PLAINTEXT://kafka:9092
    KAFKA_CONTROLLER_LISTENER_NAMES: CONTROLLER
    KAFKA_CONTROLLER_QUORUM_VOTERS: 1@kafka:9093
    KAFKA_NUM_PARTITIONS: 3
  volumes: [kafka-data:/var/lib/kafka/data]
  healthcheck:
    test: ["CMD-SHELL",
      "/opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 --list"]

Compose inicia los productores y el consumidor únicamente después de que el broker responde al healthcheck.
